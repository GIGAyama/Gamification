## note に貼る手順

1. note で新しいテキスト記事を作る
2. `manabi-quest-note-article.md` の1行目（`# 〜`）を、note のタイトル欄に貼る。行頭の `# ` は外す
3. 2行目以降を本文欄に貼る。`##` の見出しはそのまま note の見出しになり、目次が自動で作られます
4. `![…](images/…)` の行は貼っても画像になりません。**その位置で画像を手動アップロード**してください
5. 画像の下の一行（キャプション）は、note の画像キャプション欄に移してください。本文に残すと二重になります
6. ハッシュタグ欄に `#GIGAスクール` `#ICT教育` `#小学校` `#教員` `#Google Apps Script` あたり

画像は本文の流れどおりに並んでいるので、上から順に入れれば合います。対応表は下にあります。

## 撮影について（大事なところ）

**まなびクエスト本体は Google Apps Script でしか動かないため、撮影用に手もとで動かす仕組みを作って撮りました。**
画面に出ているものはすべて、リポジトリの `manabi-quest/*.gs` と `js_*.html` が実際に計算した結果です。
レベル・経験値・提出率・初回正答率・つまずき問題・声かけリストは、どれも手で書いた値ではありません。

- 使ったのは、`SpreadsheetApp` などの最小限の代わりを用意して `.gs` をそのまま Node で走らせる方法です
- そのうえで `setupDatabase()` を実行し、24人の架空の学級を作り、10週間ぶんの学習を
  `saveRecord()` / `receiveStudyLogFromPortal()` / `postAssignment()` から流しこみました
- ポータルと本体のやりとりは本番と同じホスト名（`gigayama.github.io` と `script.google.com`）で動かしています。
  この2つのオリジンは互いを厳しく検査しているので、ホスト名までそろえないと本番と同じ画面になりません

**児童の名前・きろくの中身・テストの点数はすべて架空です。** 実在の児童のデータは一切使っていません。

撮影のあいだに気づいた、記事に書くときの注意が3つあります。

1. **学習アプリのタイルの絵が、本番とちがいます。** タイルの絵は各アプリのリポジトリにある
   PWA アイコンを読み込む作りですが、撮影した環境から `gigayama.github.io` に出られなかったため、
   アプリ内蔵の代わりのアイコンが出ています（読み込めないときに空にならないための仕組みが働いた形です）。
   本番では、児童がホーム画面に入れているアイコンと同じ絵になります。
   `05-apps.png` を差しかえたい場合は、実機で同じ画面を撮り直してください
2. **アバターのアイテムの絵は、撮影用に用意した仮のものです。** アイテムの絵は先生が Google ドライブの
   フォルダに置くもので、アプリには入っていません。記事の本文では絵柄にはふれていません
3. **AI所見は「未設定」の状態で撮っています。** Gemini のAPIキーを入れていないためで、
   これは多くの学校の初期状態と同じです。記事にもそう書いてあります

## 撮り直すときの手順

撮影に使った一式は `.tmp-shots/` に置いていましたが、**納品時に削除しています。**
同じものを作り直す場合は、次の順番です。

1. `npm i --no-save playwright bootstrap@5.3.3 bootstrap-icons@1.11.3 sweetalert2@11 kuroshiro@1.2.0 kuroshiro-analyzer-kuromoji@1.1.0 kuromoji@0.1.2`
2. `manabi-quest/*.gs` を Node で読み込む土台を作る（`SpreadsheetApp` `CacheService` `PropertiesService` `LockService` `Utilities` `Session` の代わりを用意する。`new Date()` を差しかえられるようにしておくと、過去の日付のきろくを作れます）
3. `setupDatabase()` を実行し、児童マスタに名簿を入れて、`saveRecord()` などで学習を流しこむ
4. `manabi-quest/index.html` の `include()` を展開し、`google.script.run` を手もとのサーバー呼び出しに差しかえた HTML を配る
5. `/etc/hosts` で `gigayama.github.io` と `script.google.com` を `127.0.0.1` に向け、自己署名の証明書で 443 番に配る
6. Playwright を `--ignore-certificate-errors` 付きで起動して撮る

いちばん本番に近づけたい場合は、実際に Apps Script へデプロイした環境で撮り直すのが確実です。
そのときは、上の「注意が3つ」のうち1と2が解消します。

## 気づいたこと（記事とは別に、直すかどうかの判断をお願いします）

撮影のあいだに見つけた、**壊れてはいないけれど説明と食いちがっているところ**が1つあります。

**「成績・評価」タブの「学びに向かう力の評価案」は、Gemini のAPIキーを入れていないと1件も出ません。**

- 画面の説明文には「主体性の自己評価＋挙手回数（定量）」と「AIが採点した記述の深さ」を
  蓄積すると書いてあり、定量のぶんだけでも出そうに読めます
- 実際には、スコアを書き込む `recordAttitudeScore_()` が `processReflectionRow_()` の中でしか
  呼ばれず、その手前の `autoExtractShokenMaterial_()` が `isAiEnabled_()` で止まるため、
  APIキーが無いと「学びに向かう力スコア」シートに1行も入りません
- そのため「集計する」を押しても、全員のスコアが空のまま返ります（`getAttitudeSummary()` を
  直接呼んで確認しました。`rows` は返るが `scores` がすべて空）

直しかたは2つあると思います。定量のぶんだけでも先に記録するように `recordAttitudeScore_()` の
呼び出し位置を変えるか、画面に「AIのAPIキーが必要です」と出すかです。
**記事にはこの機能を「APIキーを入れたときだけ動く」とは書かず、AI所見全体としてそう書いてあるので、
どちらの直し方でも記事はそのまま使えます。**

そのほか、記事に載せた機能はすべて実際に操作して動くことを確かめました。
きろくの保存、課題のごほうびの受け取り、ガチャ、きせかえ、応援スタンプ、
ポータルからの送信、接続テスト、課題の出題と提出率の自動判定、いずれも動いています。
