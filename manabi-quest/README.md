# 🎒 まなびクエスト

小学校の学習活動を **記録 → 可視化 → ゲーミフィケーション** する Google Apps Script 製 Web アプリです。
学習記録・授業のふり返り・ゲーミフィケーション・AI所見づくりを、
**1 つのスプレッドシート・1 つの Web アプリ**で扱います。

## 設計のポイント

1. **データベースは 1 つ**
   すべてのシート（名簿・記録・ゲームデータ・所見）を 1 つのスプレッドシートに集約。`setupDatabase()` がワンクリックで全シートを自動生成します。
2. **保存時に即時経験値付与**
   記録はすべてアプリ内で保存されるため、**保存した瞬間に経験値・ミッション進捗へ反映**されます。定期バッチや済フラグ、外部シート ID の管理は不要です。
3. **記録は保護者向け資料・所見に活用**
   - 学期末に全児童分の **学習ポートフォリオPDF**（記録＋ふり返り＋ゲーム実績）を自動生成
   - ふり返り記述から **AI が所見材料を抽出** → 全体所見・道徳所見を AI 生成（Gemini / 任意機能）
4. **評価支援も転記レスで自動化**
   - 児童はテストのふり返りで**目標点**を立て、点数との差がバッジとグラフで見える（自己調整学習の支援）
   - 教員の「成績・評価」タブに、テストのふり返りから自動集計した**成績マトリクス（児童×単元・クラス平均・目標未達ハイライト）**を表示。成績シートへの転記作業が不要に
   - 授業のふり返り保存のたびに「主体性の自己評価＋挙手回数（定量）」と「AIが採点する記述の深さ」を**学びに向かう力スコア**として自動蓄積（AI採点は所見材料抽出と同じ1回のAPI呼び出しに相乗り）。学期平均から**A/B/C評価案**をワンクリックで集計・シート出力
   - 所見ドラフトは**要録用（だ・である調）へのAI変換**もワンクリック
5. **AI所見材料の自動ストック（指導事項との照合）**
   - 教員が「指導事項」シート（アプリの「AI所見」タブから登録可）に単元名・ねらいを登録しておくと、児童が授業/テストのふり返りを**保存した瞬間**に AI が記述を分析
   - 指導事項と照合したうえで、学習指導要領の**3観点タグ・おすすめ度つき**のエピソードとして「所見材料」シートへ自動ストック（めあての達成・挙手回数・目標点との差などの定量データも分析に使用）
   - 保存時に処理できなかった分は「所見抽出」フラグが空のまま残り、教員画面のボタンまたはシートメニューの一括抽出があとから回収
   - ストックした材料から、教員画面のワンクリックで**全体所見のドラフトを AI 生成**（「全体所見」シートにも保存）。**全児童分の一括生成**・**道徳所見の生成**・**要録用文体への変換**にも対応
   - 指導事項は表計算ソフトからの**貼り付け一括登録**が可能
6. **児童の学びを深める仕掛け**
   - **ふり返り質ボーナス**: AIが評価したふり返りの深さに応じてボーナス経験値。「たくさん書く」から「深く書く」への動機づけ（設定でON/OFF・係数調整可、追加API不要）
   - **書き出しヒント**: ふり返り入力欄にワンタップの書き出しチップ（「今日わかったのは…」等）。記述の質が上がり、AI抽出・評価の精度も向上
   - **AIコーチ**: ふり返りを保存した瞬間に、AIが児童本人へ「みとめの言葉＋次の小さな一歩」を返します。
     所見材料の抽出と**同じ1回のAPI応答に相乗り**しているので、API呼び出し回数は増えません
6.5. **努力の成果を実感できる仕掛け**（詳細は後述の専用セクション）
   - **がんばりカレンダー**（学習ヒートマップ）と**連続きろく日数**で、毎日の積み重ねを可視化
   - **じこベスト更新**の演出。上位に届かない児童にも「きのうの自分」という勝てる相手を用意
   - **わたしの成長カード**（今月 vs 先月）・**学びの総量メーター**（読んだページ＝本◯冊分 など）
   - **めあて（目標）を全教科・全種目へ**。進捗はきろくから自動計算され、児童の手入力は不要
   - **週次ふり返り**。今週のまとめを見ながら3つの質問に答え、「来週のめあて」がそのまま次のめあてになる
   - **わたしのことばアルバム**と**むかしの自分**カードで、過去のふり返りを読み返せる
   - **クラス共同目標ゲージ**・**応援スタンプ**・**みんなの本だな**でクラスの学びをつなぐ
   - ランキングに**今週ののび／けいぞく／どくしょ王**など、誰でも1位になれる軸を追加
7. **教師の負担を減らす運用支援**
   - **声かけリスト**: 無記録が続く／授業「むずかしかった」が連続／テスト目標に連続未達の児童を、ダッシュボードに自動表示（ルールベース・AI不要）。カードから児童詳細へ即移動
   - **週次クラスサマリーメール**: 毎週月曜の朝、先週の記録件数・活発／無記録の児童・声かけリスト・所見づくりの状況を担任へ自動メール（時間主導トリガー）
   - **面談メモPDF**: 児童詳細からワンクリックで、成績（目標→結果）・がんばり・所見材料・最近のふり返り＋メモ欄をA4一枚に
   - **がんばり賞状PDF**: 学期末に児童ごとの賞状（ベスト記録・獲得バッジ・AIが作った成長エピソード）を一括生成
   - **年度末アーカイブ**: 記録・ログ・所見を別スプレッドシートへ退避し、記録シートを空にして新年度をまっさらに（マスタ・設定は保持）
8. **AI連携の堅牢化**
   - 既定モデルは `gemini-2.0-flash`。レート制限（429）や一時エラーは**指数バックオフで自動再試行**し、一括処理の取りこぼしを軽減
9. **学習アプリ連携 — study.v1 共通学習ログの収集・活用**（詳細は後述の専用セクション）
   - GIGA山 学習アプリ群（Qalc・漢字タウン・けいさんカード・さんすうブロック・100マス計算・九九カード・どくしょ ちょきんばこ・Typa）が端末に保存する**共通学習ログ（study.v1）の受信側（収集サーバー）**をこのアプリに内蔵
   - **「まなびクエストと同じ画面」から送信できる**: 学習ポータル（[`../manabi-portal/`](../manabi-portal/)）がまなびクエストを iframe で表示し、アプリ内の「きろくを おくる」ボタンからそのまま送信できます
   - **タイピング・100マス計算・読書は手入力なし**。Typa／100マス計算アプリ／どくしょ ちょきんばこ のきろくから「タイピング記録」「100マス計算記録」「読書記録」シートへ自動転記され、ランキング・バッジ・ミッション・めあて・グラフに反映されます
   - 教員用「学習アプリ」タブで、**初回正答率・学習時間・クラスのつまずき問題**（何人が同じ問題を落としたか）を横断集計。児童詳細・週次サマリーメールにも反映
   - 受信したログは**経験値に変換**され、さらに**そうしんボーナス・れんぞくボーナス・交換ポイント**が付くので、「きろくを送ること」自体が児童のはっきりした得になります

## セットアップ手順

### 1. スプレッドシートとスクリプトの準備

1. 新しい Google スプレッドシートを作成する
2. 「拡張機能 → Apps Script」を開き、このフォルダの各ファイルを作成する
   - `.gs` ファイル → そのままの名前でスクリプトファイルとして追加（**01→10 の順に作成**）
   - `index.html` / `css.html` / `icons.html` / `js_core.html` / `js_student.html` / `js_teacher.html` → HTML ファイルとして追加
   - `appsscript.json` → プロジェクト設定で「マニフェストを表示」を ON にして内容を置き換え
3. スプレッドシートに戻って再読み込みし、メニュー **「🎒 まなびクエスト管理」→「① 初期セットアップ」** を実行
   → 全シートがヘッダー・初期設定・サンプルミッション/バッジつきで生成されます
4. すでに運用中のスプレッドシートを更新した場合は、続けて
   **「③ 新しいミッション・バッジを追加」** を実行してください
   （「① 初期セットアップ」は、データが入っているミッション・バッジシートには追記しません。
   ③ は**まだ無いIDの行だけ**を足すので、先生が編集・追加した行はそのまま残ります）

### 2. 名簿の登録

「児童マスタ」シートに入力します。

| 出席番号 | 名前 | ニックネーム | メールアドレス | 累計経験値 | 経験値 | 交換ポイント | 最終ログイン日 |
|---|---|---|---|---|---|---|---|
| 1 | 山田太郎 | たろう | taro@example.jp | 0 | 0 | 0 | |
| `担任` | 佐藤先生 | さとう | sato@example.jp | | | | |

- **出席番号に「担任」と入れたアカウントが教員用画面**になります
- 児童マスタにないアカウントはアプリを利用できません（登録案内が表示されます）

### 3. Webアプリとして公開

「デプロイ → 新しいデプロイ → ウェブアプリ」で作ります（実行ユーザーは **自分**）。
**必要なのは本体のデプロイ 1 つだけ**です。

| 用途 | アクセスできるユーザー | 必須 | 使い道 |
|---|---|---|---|
| **本体** | **組織内の全員**（学校ドメイン） | ✅ | 児童・教員が使うアプリ本体。学習ポータルの iframe に表示し、**学習ログの送信もこの画面ごしに行います** |
| **学習ログ受信用** | **全員**（匿名） | 任意 | まなびクエストを表示できない環境むけの予備の受け口（匿名POST） |

#### 「アクセスできるユーザー」に **全員** が出てこないとき（組織アカウント）

学校（Google Workspace）のポリシーによっては、デプロイの選択肢に **全員** が出ず
**組織内**しか選べないことがあります。**この場合もそのまま使えます。**

学習ポータルは、まず **本体のデプロイごしに学習ログを送ります**（本体経由）。
ポータルは iframe に表示しているまなびクエストへ記録を渡し、
**すでに学校アカウントでログインしているその画面**が `google.script.run` で
サーバーの `receiveStudyLogFromPortal()` を呼びます。
ログイン済みのセッションの中での呼び出しなので、アクセスが **組織内** のままでも通り、
CORS も匿名アクセスも必要ありません。

- 受信用デプロイ（アクセス: 全員）と **学習ログ送信キー** は**任意**です。空欄のままで運用できます
- 管理者に依頼して外部共有を許可してもらう必要は**ありません**
- 児童は学校アカウントでログインしている必要があります（もともとアプリ本体の利用に必要です）
- **児童が出席番号を入力する必要はありません**。ログイン中のアカウントから特定するので、
  入力ミスや前の児童の番号が残っていることによる取りちがえも起きません

> 逆に、本体を iframe で表示できない環境（サードパーティ Cookie を強く制限している等）が
> ある場合にそなえて、**全員**を選べるなら受信用デプロイも作っておくと確実です。
> ポータルは本体経由がだめだったときだけ、自動でそちらへ切り替えます。

### 4. 学習ポータルを配付する

児童に配るURLは、本体のWebアプリURLではなく **学習ポータル** にします。

```
# 本体経由だけで運用する場合（組織アカウントで「全員」を選べないときはこちら）
https://gigayama.github.io/Gamification/manabi-portal/?app=<本体URL>

# 受信用デプロイ（アクセス: 全員）も併用する場合
https://gigayama.github.io/Gamification/manabi-portal/?app=<本体URL>&endpoint=<受信用URL>&key=<学習ログ送信キー>
```

ポータルはまなびクエストを iframe で表示しつつ、学習アプリの学習ログ送信も担当します
（配置手順は [`../manabi-portal/README.md`](../manabi-portal/README.md)）。
本体URLを直接開いても通常どおり使えますが、その画面から学習ログを送ることはできません
（「初期設定」の `学習ポータルURL` を入れておくと、児童画面にポータルへの案内ボタンが出ます）。

| 機能 | 設定方法 |
|---|---|
| アバター画像 | ドライブのフォルダに `0001.png` 形式で画像を置き、「初期設定」にフォルダ ID を記入 → メニュー「② アイテム画像のIDを自動登録」。アイテムは「アイテムマスタ」に登録（カテゴリはアバター構成シートの列名と対応） |
| AI 所見機能 | Apps Script の「プロジェクトの設定 → スクリプト プロパティ」に `GEMINI_API_KEY` を追加 |
| AI所見材料の自動抽出 | 「初期設定」の `AI所見材料の自動抽出` が `ON`（既定）だと、ふり返り保存時に自動でAI分析（`OFF` にすると一括抽出のみ）。「AI所見」タブで指導事項（単元・ねらい）を登録すると照合精度が上がります |
| 道徳AIフィードバック | 「初期設定」の `道徳AIフィードバック` を `ON` に（保存時に自動生成。Classroom コース ID を設定すると個別配信も可能） |
| 学びに向かう力の評価基準 | 「初期設定」の `人間性評価_A基準` `人間性評価_B基準`（学期平均の閾値）、自己評価◎◯△の点数・挙手最大加点・AI評価最大点を調整可能 |
| ふり返り質ボーナス | 「初期設定」の `ふり返り質ボーナス`（ON/OFF）と `ふり返り質ボーナス係数`（深さ×係数=ボーナスEXP） |
| テストの経験値バランス | 「初期設定」の `テストふり返り経験値方式`（`線形`／`二乗`）・`テストふり返り経験値_線形係数`・`テストふり返り経験値上限`。**標準は「線形」**（後述の「経験値のバランス」参照） |
| 日々の積み重ねのごほうび | `連続きろくボーナス係数` / `連続きろくボーナス上限日数` / `自己ベスト更新ボーナス経験値` / `週次ふり返り経験値`（いずれも 0 で無効） |
| 応援スタンプ | `応援スタンプ経験値_おくる` / `応援スタンプ経験値_もらう`（0 で無効。1日に送れる数は5件で固定） |
| がんばりカレンダー | 「初期設定」の `がんばりカレンダー週数`（既定12週） |
| 声かけリストのしきい値 | 「初期設定」の `声かけアラート_無記録日数` `声かけアラート_連続未達回数` |
| 週次サマリーメール | シートメニュー「📧 週次サマリーメール → 自動送信を設定」で毎週月曜朝に担任へ配信（担任のメールを児童マスタに登録しておく） |
| 学習アプリ連携 | 「初期設定」の `学習ポータルURL` にポータルのURLを設定（`学習ログ送信キー` は匿名の受信用デプロイを併用するときだけ） → 後述「学習アプリ連携」参照 |
| 送信ボーナスの調整 | 「初期設定」の `学習ログ送信ボーナス経験値` `学習ログ連続ボーナス係数` `学習ログ連続ボーナス上限日数` `学習ログ送信ボーナス交換ポイント`（0 で無効） |
| 経験値のバランス | すべて「初期設定」シートで調整可能（係数・固定値・ガチャ排出率など） |

## 画面構成

### 児童用

**設計の原則: 1つの画面に「えらぶ・入力するもの」を3つまで。**
情報をならべるのではなく、`タブ → 入口 → えらぶ → 中身` の階層に分け、
1画面ずつ進んでいく形にしています。奥に入るときは右から、戻るときは左から
画面がスライドし、**出ていく画面とすれちがう**ので、いま自分がどこへ動いたのかが
文字を読まなくても分かります（→ [画面が動くところ](#画面が動くところ楽しさの仕掛け)）。

- **低学年対応: 漢字に自動ふりがな** — 児童画面に出るすべての漢字の上に、ひらがなのルビを自動表示（教科名・単元名・本のタイトル・AIコメント・自分のふり返りなど動的な文章も対象）。教員画面には付きません
- **低学年対応: 文字サイズの切りかえ** — ヘッダーの「あ あ あ」で **ふつう / 大きい / もっと大きい** を選べます。
  `<html>` のクラスで rem の基準を変えるので、文字だけでなくボタン・カード・余白まで一緒に大きくなります。
  選んだ大きさは `localStorage` に覚えます（保存できない環境ではその場かぎりの設定として動きます）
- **どの画面からも1タップで戻れる** — 奥の画面には必ず「← もどる」がつきます。
  下部バーの「もどる」・画面端からのスワイプ・ブラウザの戻るも、同じ1階層ぶんだけ戻ります

#### タブは4つ

| タブ | 入口の画面に置いてあるもの（3つまで） |
|---|---|
| 🏠 **ホーム** | ①**きょうのやること**（1つだけ）／②きろくをつける／③ミッション・めあて |
| ✏️ **きろく** | きろくの種類のグループ2つ（じゅぎょうのふり返り／じぶんのこと）。タイピング・100マス計算・どくしょはアプリから自動で入るため、ここにはありません |
| 🌟 **マイページ** | がんばりを見る／きろくを見かえす／ガチャ・きせかえ |
| 👫 **みんな** | クラスの目標／おうえんする／ランキング・本だな |

#### ホーム: 「きょうのやること」は1つだけ

上に自分の状態（アバター・レベル・経験値バー・けいけんち／こうかんPt／れんぞくきろく）を出したあと、
**いま一番やってほしいことを1つだけ**、大きなカードで出します。何をすればよいか迷わせないためです。
`pickTodayTask()` が上から順に見て、最初に当てはまったものを出します。

1. 端末にたまっている学習アプリのきろく → **おくろう**
2. 受けとっていないミッションのごほうび → **うけとろう**
3. 今週のふり返りがまだ（週の後半） → **ふり返ろう**
4. 今日まだきろくを書いていない → **きろくをつけよう**
5. めあてがない → **めあてを立てよう**
6. ぜんぶ終わっている → **きょうはかんぺき！**（緑色になります）

#### きろく: しつもんに1つずつ答えていく

`グループをえらぶ → 種類をえらぶ → 1問ずつ答える` の3段階です。

- 入力欄をたくさんならべた「紙のプリント」ではなく、**1画面に しつもん1つ**。
  上の点（`.mq-dots`）とバー（`.mq-progress`）でいま何問目かが分かり、「つぎへ」で進みます。
  1問こたえるたびに、その点が「ぽん」とはじけて緑になり、バーがのびます
- すべてのステップは最初から DOM に置いてあり表示だけを切りかえるので、前に書いた内容は消えません
- 数はステッパー（＋−ボタン）、3択などは**押して選ぶボタン**。小さなプルダウンをさわらずに入力できます
- ふり返り欄には**書き出しヒント**のチップ（「今日わかったのは…」等）
- 保存すると紙ふぶき（四角・まる・星）が舞い、経験値の数字がカウントアップして経験値バーが光ります。
  レベルアップしたときは、画面いっぱいに光の輪がひろがる専用の演出が入ります（自己ベスト更新はさらに派手に）
- 保存後は「なにを きろくする？」の入口までもどるので、続けて別のきろくも書けます
- テストのふり返りは**目標点→結果**を記録し、目標との差バッジ＆教科別の点数・目標推移グラフで自己調整学習を支援
- 授業・テストのふり返りには、保存時にAIが返した**AIコーチのひとこと**が並びます
- タイピング・100マス計算・どくしょは、それぞれ Typa／100マス計算アプリ／どくしょ ちょきんばこ のきろくから自動で入るため、入力画面はありません

質問の数: せいちょう2 / じしゅ学習3 / じゅぎょう6 / テスト5 / どうとく3

#### 画面が動くところ（楽しさの仕掛け）

「どこにいるか」「何が起きたか」を、文字を読まなくても**動きで**分かるようにしています。

| いつ | 何が起きるか | しくみ |
|---|---|---|
| タブを移る | 右どなりのタブなら右から、左どなりなら左から画面が入ってきます。押したタブの絵も「ぴょん」とはねます | `viewDirection_()` → `.spa-view.from-right` / `.from-left` |
| 奥の画面へ入る／戻る | 入る画面と**出ていく画面がすれちがい**ます（前の画面は反対がわへすべって消えます） | `goPanel()` → `leavePanel_()` → `.mq-panel.leaving.out-fwd` / `.out-back` |
| とびらを押す | 本体がぐっと沈み、光がさっと横切り、矢印が先に走っていってから次の画面へ | `tapDoorThen()` → `.mq-door.tapped` |
| きょうのやること | ときどき光が横切って目をひきます。やりおえたしゅんかんはカードがうなずきます | `.mq-today::before` / `.mq-today.just-done` |
| しつもんに答える | いま答えた点が「ぽん」とはじけて緑になり、下のバーがのびます | `showStep()` → `.mq-dots i.just-done` / `.mq-progress` |
| けいけんちがふえる | 数字がカウントアップし、経験値バーの上を光がすべります | `countUp()` / `setXpBar_()` → `.mq-xpbar.grew` |
| レベルアップ | 画面いっぱいに光の輪が3つひろがり、あたらしいレベルが飛び出します（**演出が終わってから**ダイアログ） | `showLevelUp()` → `levelUpBurst()` |
| ごほうびを受けとる／ガチャ | 押したところから星がはじけ飛びます | `starBurst(el)` |
| 一覧が出てくる | ミッションやランキングが上から順にふわっと出ます | `.mq-stagger` |
| 読み込み中 | まるが3つ、じゅんばんにぴょんぴょんはねます | `.mq-loading-dots` |
| ボタンを押して待つ | 押したボタンの中でくるくる回ります（画面はふさぎません） | `busyApi()` → `.is-busy` / `.mq-spin` |

**動きを減らす設定**（`prefers-reduced-motion: reduce`）の端末では、
画面遷移のアニメーション・紙ふぶき・レベルアップの演出・星のはじけを自動でオフにします
（とびらも待たずに、すぐ次の画面へ進みます）。
ボタンのくるくるだけは「いま待っている」ことを伝える合図なので、ゆっくりにするだけで止めません。

#### 待たせ方と、押したあとの見え方

サーバーは Google スプレッドシートなので、どの操作も **0.5〜2秒** かかります。
そこをどう見せるかで体感が大きく変わるため、次の3つを守っています。

**① 待つ場所は、押したボタンの中**

| つかうもの | いつ | 見え方 |
|---|---|---|
| `busyApi(btn, ラベル, 関数名, ...)` | ふつうの操作（ごほうび・きろく保存・ガチャ・こうかん・応援・ほぞん） | 押したボタンがくるくる回る。画面は見えたまま。二重タップはここで止まる |
| `apiWithLoading(文言, 関数名, ...)` | PDF作成・AI生成など、待つあいだ他をさわられると困る重い処理だけ | 画面全体をふさぐ。ただし **400ms 以内に返ってきたときは出しません**（一瞬の暗転はかえって遅く見えるため） |

ボタンの幅は押す前のまま固定します（`busyButton()`）。
ミッションの「うけとる！」のような小さなボタンは **ラベルを渡さず** くるくるだけにしてください。
文字を入れると幅が広がり、まわりがガタッとずれます。

**② 返事が来たら、演出より先に画面を書きかえる**

「おめでとう」の紙ふぶきが出ているのに、うけとるボタンがまだ残っている——
という食いちがいを作らないため、**表示の更新 → 演出** の順に必ず書きます。
けいけんち・交換Pt・レベル・つぎのレベルまでのバーは
`applyProfileGains_(res)` → `syncProfileDisplay_()` の1本道にまとめてあります。

**③ 取り直しは、できるだけしない／隠す**

サーバーの関数は、画面を書きかえるのに要るものを**返り値にすべて入れて**返します
（`claimMissionReward` なら `levelInfo` や `rewardType` まで）。
だから、ごほうびの受け取りは **サーバーとのやりとり1回だけ** で完結し、
「受け取ったのに、しばらくボタンが残ったまま → また読み込み」になりません。

どうしても全体を取り直す必要があるとき（学習ログの受信のあとなど）は、
**おいわいのダイアログを出すのと同時に**うしろで取りにいきます（`refreshStudentData()`）。
児童が「やったね！」を読んでいるあいだに更新が終わるので、閉じたあとに待たされません。

ミッションの一覧は、中身が変わっていなければ描き直しません（`missionSignature_()`）。
顔ぶれが変わったときだけ `.mq-stagger` で上から順に出し、
進み具合が変わっただけのときはその場で書きかわります（毎回出なおすと、ちらついて見えます）。

### アイコン（`icons.html`）

絵文字は端末（Windows / iPad / Android）ごとに絵柄も色もちがい、画面のデザインとそろいません。
そこで児童画面のアイコンは、`icons.html` にまとめた **自前の SVG** に統一しています。

- **形のきまり**: 32×32 のマス目・角を丸めたシンプルな形・2階調（うすい面＋こい面）
- **色は指定しない**: `fill="currentColor"` なので、置いた場所の文字色になります。
  とびら（`.mq-door`）やカード（`.mq-card`）のアクセント色に**自動でそろいます**
- **つかい方**: JS なら `icon('home')`、HTML なら
  `<svg class="mq-icon"><use href="#i-home"></use></svg>`
- **大きさ**: `1em` なので、置いた場所の文字サイズで決まります。
  文字サイズを「大きい」に切りかえると、アイコンも一緒に大きくなります

> ⚠️ `<use>` はシャドウツリーを作るため、**外側の CSS クラスはアイコンの中まで届きません**。
> `fill` は継承されるので `currentColor` は効きますが、`opacity` は継承されません。
> うすい面は `opacity=".28"` のように **SVG の属性として直接** 書いてください
> （クラスで指定すると、すべて同じ濃さのベタ塗りになります）。

例外として、記号そのものに意味がある次のものは絵文字・記号のまま残しています。

| 残しているもの | 理由 |
|---|---|
| ◎ ◯ △ | 日本の学校で使う評価記号。絵にすると意味が伝わりません |
| 応援スタンプ | 「初期設定」シートで先生が変えられるデータです。よく使う 👏🔥💖💪⭐ は `stampIcon()` が自前アイコンに置きかえ、知らない絵文字はそのまま表示します |
| 教員画面のアイコン | Bootstrap Icons のまま（児童画面のみ刷新の対象です） |

ランキングの 1〜3 位は 🥇🥈🥉 をやめ、画面の色づかいにそろえた金・銀・銅のバッジ（`.rank-badge`）にしています。

### どの端末でも使いやすく（スマホ・タブレット）
- **表示領域を最大化** — コンテンツは固定幅ではなく画面幅いっぱい（大画面では最大1440px）に広げ、
  スマホではナビゲーションの高さを詰め、タブ行を画面上部に貼り付けて常に押せるようにしています
- **画面下部のナビゲーションバー** — Webアプリを直接ひらいたときに「◀ もどる」を表示します
  （学習ポータル＝PWA の中で開いているときは、ポータル側の下部バーを使うので表示しません）
- **戻る操作** — 「もどる」のタップ／**画面の左右の端から中央へのスワイプ**／ブラウザの戻る（Alt+←）は
  すべて「1つ前の階層へ戻る」に統一。タブ移動・サブタブ移動・入力フォーム・ダイアログが対象です。
  ジェスチャーとブラウザの戻るが同時に起きても、戻るのは1階層だけです

| **連続きろく日数** | 「◯日れんぞくきろく中！」をホームの目立つ場所に表示。最長記録も併記 | 同上 |
| **じこベスト更新** | タイピングの速さ・テストの点数・100マスのタイム（100問）が自己ベストを更新すると、専用の演出とボーナスEXP | 各記録シート（保存の**前**の値と比較）。タイピングと100マスは**学習ログの受信時**に判定します |
| **わたしの成長カード** | 今月 vs 先月を、きろく数・きろくした日・読んだページ・タイピングの速さ・学習アプリ時間・初回正答率で比較。ほめる文は**ルールベース生成（AI不要）** | 各記録シート＋学習ログ |
| **学びの総量メーター** | 「読んだページ＝本◯冊分」「打った文字＝原こう用紙◯まい分」など、実感しやすい単位へ換算 | 読書記録・タイピング記録・学習ログ |
| **まなびレーダー** | 教科ごとのとりくみ度を0〜100で表示（ふり返りの数＋テストの平均点）。Google Chartsにレーダーが無いため**SVGを自前で描画** | 授業/テストのふり返り |

### ふり返りの循環（めあて → 学習 → ふり返り → 次のめあて）

- **めあて（目標）を全種目へ** — タイピング／読書のページ数／100マスの回数／自主学習の回数／学習アプリの時間／**自分で決めためあて（自由記述）**。
  期間は「今週」「今月」から選べ、**種類ごとに1つずつ**挑戦できます（以前はアプリ全体で1つだけでした）
- **進捗は自動計算** — 児童は入力しません。きろくから集計した実績が進捗バーに出て、100%になった時点で達成＆ボーナスEXP。
  自由記述のめあてだけは数値で測れないため、児童が自分で「できた！」を押します
- **週次ふり返り** — 今週のまとめ（きろく数・きろくした日・読んだページ・学習アプリ時間・じこベスト更新・連続日数）を見ながら3つの質問に回答。
  **「来週のめあて」はそのまま自由記述のめあてとして自動登録**され、ここで循環が閉じます。木曜以降、未記入ならホームで目立ちます
- **めあての達成率** — 「立てためあてのうち何%を達成したか」をホームに常設表示
- **わたしのことばアルバム** — 過去のふり返りを新しい順に読み返せる一覧。加えてホームに **「◯か月前のあなた」** を1枚だけ表示します
  （30日以上前のものから、日付をたねに選ぶので1日のあいだは同じものが出ます）
- **AIコーチ** — ふり返り保存時のAI応答に `studentComment`（みとめの言葉）と `nextGoalHint`（次の小さな一歩）を追加。
  所見材料の抽出と同じ応答なので**API呼び出しは増えません**。APIキー未設定・失敗時は何も出ずに通常保存されます

### 仲間とのつながり

- **クラス共同目標ゲージ** — 「協力」ミッションをひろばに大きなゲージとして常設表示。ミッションマスタに行を足すだけでゲージが増えます
- **応援スタンプ** — 今週がんばっている友だちに、定型スタンプ（👏🔥💖💪⭐）を送れます。
  **自由記述は持たせず**、同じ相手には1日1回・1日あわせて5回までにして、トラブルを構造的に防いでいます。送る側・もらう側の両方にEXP
- **みんなの本だな** — クラスの読書記録を1冊ずつまとめ（ISBN があれば ISBN で同定）、読んだ人数・平均評価・おすすめコメントを表示
- **ランキングの再設計** — 絶対値のランキングは上位が固定されがちなので、
  **今週ののび（先週比）／けいぞくチャンピオン（連続きろく日数）／今週のがんばり／どくしょ王**を上位に置きました
- **先生からのひとこと** — 教員の児童詳細画面から、定型スタンプ＋短文をその児童だけに送れます（お知らせシートの`宛先`つきの行）

### 経験値のバランス（重要な変更）

テストのふり返りは従来 `floor(0.1 × 点数²)` で、**100点×2観点＝2000EXP** でした。
日々の記録（20〜50EXP）の40〜100倍にあたり、「毎日の積み重ね」の価値が見えにくくなるため、**標準を「線形」に変更**しています。

| 方式 | 計算 | 100点×2観点 |
|---|---|---|
| **線形（標準）** | `min(floor(点数 × 係数), 上限)` を観点ごとに加算 | 200EXP |
| 二乗（従来） | `floor(係数 × 点数 × 点数)` を観点ごとに加算 | 2000EXP |

**従来どおりに戻したい場合**は「初期設定」の `テストふり返り経験値方式` を `二乗` にしてください（既存の `テストふり返り経験値係数` がそのまま使われます）。

あわせて、日々の努力側に次のごほうびを追加しました（すべて「初期設定」で調整でき、0 で無効化できます）。

| ごほうび | 計算 | 設定キー |
|---|---|---|
| 連続きろくボーナス | その日はじめてのきろくに `min(連続日数, 上限) × 係数` EXP | `連続きろくボーナス係数` / `連続きろくボーナス上限日数` |
| じこベスト更新ボーナス | 自己ベストを更新したときの固定EXP | `自己ベスト更新ボーナス経験値` |
| 週次ふり返り | 今週のふり返りを1回書いたときの固定EXP | `週次ふり返り経験値` |
| めあて達成 | めあてを1つ達成したときの固定EXP（全種目共通） | `目標達成ボーナス経験値` |
| 応援スタンプ | 送ったとき／もらったときのEXP | `応援スタンプ経験値_おくる` / `応援スタンプ経験値_もらう` |

## 学習アプリ連携（study.v1 共通学習ログの収集）

「学習ログ共通スキーマ仕様書 `study.v1`」（1.9）に基づき、GIGA山 学習アプリ群
（gigayama.github.io 配下の Qalc / 漢字タウン / けいさんカード / さんすうブロック / 100マス計算 / 九九カード / どくしょ ちょきんばこ / Typa）の
学習データを収集・活用します。まなびクエストは仕様でいう**受信側（サーバー / GAS）**にあたります。

```
学習アプリ（保存のみ / 匿名）
  └─ localStorage: study.records.v1
       └─ 学習ポータル（../manabi-portal/ を GitHub Pages で公開）
            │    ├─ まなびクエスト本体を iframe で表示（postMessage で送信を依頼できる）
            │    └─ たまっているきろくを自動／ボタンで送信
            ├─ ① 本体経由 → まなびクエストの画面 → receiveStudyLogFromPortal（既定）
            └─ ② 匿名POST → まなびクエスト doPost（アクセス「全員」のデプロイがあるときだけ）
                 ├─ 検証（仕様 §9: schema / UUID / appId / 数値範囲 / サイズ）
                 ├─ 重複排除（レコードID）・時刻の丸め（§4.1: 日付＋時間帯）
                 ├─ 「学習ログ」シートへ保存
                 ├─ 100マス計算アプリの分は「100マス計算記録」シートへ自動転記
                 ├─ どくしょ ちょきんばこの分は「読書記録」シートへ自動転記
                 ├─ Typa の分は「タイピング記録」シートへ自動転記
                 └─ 経験値・送信ボーナス・交換ポイントを付与（ゲーミフィケーション接続）
```

### なぜポータルが親で、アプリが iframe なのか

学習ログは学習アプリと同一オリジン（gigayama.github.io）の `localStorage` にあり、
**ブラウザのストレージ分離により、サードパーティ iframe からは読めません**。
そのため「まなびクエストの中に github.io を iframe で置く」構成は成立せず、
**ポータル（github.io）を親ページ、まなびクエストを iframe** にしています。
アプリ内のボタンは `postMessage` で親ページに送信を依頼するため、
児童からは「まなびクエストの中に送信ボタンがある」ように見えます。
`doGet` は iframe 表示のため `XFrameOptionsMode.ALLOWALL` を指定しています。

### セットアップ

これだけで送信できます（本体経由）。次の 4・5 は、**アクセス「全員」のデプロイを作れる場合の任意設定**です。

4. 「初期設定」の **`学習ログ送信キー`** に合言葉を設定（空欄の間は匿名POSTの受信を停止します。

### 拒否したレコードの扱い（仕様 §9.3）

受け取れなかったレコードは `rejected: [{ id, reason, retryable }]` として送信ページへ返します。
`retryable` は**そのレコードを端末から消してよいか**を表します。

| 種別 | `retryable` | 例 | 送信ページの動作 |
|---|---|---|---|
| 恒久エラー | `false` | `schema` / `id` / `count` などが不正、`source: teacher`（記録対象外） | 削除してよい |
| 一時エラー | `true` | `appId` が許可リストに無い（**受信側が未対応なだけ**） | **削除せず端末に残す** |

一時エラーを「送信済み」として消すと、**児童が学習したきろくが誰にも気づかれないまま永久に失われます**
（受信側を直しても、消えたレコードは戻りません）。判定は `STUDY_RETRYABLE_REASONS` にまとめてあります。

ポータルは残したレコードの件数と、いちばん古い学習日を画面に表示します。
**件数がいつまでも減らないときは、許可リストの更新もれを疑ってください。**

### 集計の考え方（仕様に準拠）

- **主指標は「初回正答率」**（`firstTryCorrect / attempted`）。正解するまで先へ進めないアプリでも意味が揃う唯一の指標です（仕様 §2.7）
- 初回正答率は **通常出題（course）× 客観採点（objective）× ソロプレイ** のレコードだけで計算します。
  復習・にがて出題（母集団が偏る）、自己評価（採点の意味が違う）、対戦モード（妨害要素あり）は
  学力指標に混ぜず、**取り組み量（回数・時間）としてのみ**数えます（§2.4 / §2.9 / §3.2 / §5.5）
- **つまずき問題**は設問層（`items`）から「初回で誤答した児童の人数」を集計します。児童が自作した問題（custom）は
  設問IDの意味が児童ごとに異なるため対象外です（§2.4）
- 学習時間は `activeMs`（実際に操作していた時間）を優先し、なければ `elapsedMs` を使います（§2.8）
- 設問層が200件の上限で切り詰められたレコード（`ext.itemsTruncated` を持つもの）は、
  `summary` が切り詰め後の `items` に合わせてあります。集計では退避された**本当の解答数・初回正答数**を
  使うので、長く取り組んだセッションが「未着手が多い」と誤って読まれることはありません（§2.7）
- **1台の端末を交代で使うモード**（九九カードの「ふたりでもんだい」など）は `multiplayer: true` で届き、
  設問層を持ちません。他の児童の解答が混ざっているため、**取り組み量としてのみ**数えます（§2.4.1）
- **`aborted`（中断）は事実の記録であって評価ではありません。** 中断が正常な使い方であるアプリ
  （`STUDY_ABORT_NORMAL_APPS` ＝ 現在は Typa）は「中断」の回数に数えません（§5.4）

### 指導のてがかり（拡張層 `ext` の利活用）

回数と正答率だけでは「次に何をすればいいか」までは決まりません。
先生の「学習アプリのとりくみ」画面には、各アプリが固有に記録している値（拡張層 `ext`）のうち、
**明日の指導の判断を変えられるもの**だけをカードで出します（`buildStudyTeachingHints_`）。

| てがかり | 出どころ | 明日の指導のどこが変わるか |
|---|---|---|
| 漢字の4技能（よみ／いみ／かき／ひつじゅん） | 漢字タウン `ext.skills`（§3.3） | 「読めるが書けない」学級なら、書く時間を増やす |
| ひき算の作戦べつの定着（減加法／減減法） | さんすうブロック `ext.strategyStats`（§3.5） | 減減法だけ低ければ、その作戦を教え直す |
| タイピングのミスの多い指 | Typa `ext.missByFinger`（§3.9） | 右こゆびのミスが多い＝人さし指2本打ちの癖。運指指導の的が絞れる |
| 100マス計算の入力のしかた | 100マス計算 `ext.input`（§3.6） | 手書きとキーボードのタイムを同じ土俵で並べない |
| つまずき問題の**よくある誤答**・ヒント使用 | 設問層の `wrong` / `hint`（§2.10） | 「18人が落とした」に加え、**どう間違えたか**が分かる |

- 拡張層はアプリごとに意味が違うため、**アプリをまたいだ集計には使いません**（§2.11）。
  カードもアプリ単位で閉じています
- 出す項目は仕様 §4.2 の基準（**この値が明日の指導のどの判断を変えるかを1文で言えること**）で選びました。
  1文が書けない値は、届いていても画面には出していません
- 漢字の4技能は「いまの習熟度」であって1回ぶんの成績ではないため、足し合わせず
  **児童ごとにいちばん新しい1件**をとって平均します（熱心な児童ほど重みが増すのを避けるため）
- 打ち直し（Typa のおまけの周）のミスは正答率の分母には入りませんが、
  つまずきとしては同じ価値があるので `ext.retry` のぶんも指べつの集計に足します（§3.9.3）
- 届いていないてがかりはカードごと出しません（空欄が並ぶと「0なのか未受信なのか」が分からなくなるため）

### プライバシー（仕様 §4）

- アプリ層・レコードには児童名を含めず、識別は**出席番号**のみ。
  本体経由（既定）ではログイン中のアカウントから、匿名POSTでは送信ページが付与した番号から決まります
- 学習開始時刻は既定で**「日付＋時間帯（午前/午後/夕方以降）」に丸めて保存**します（§4.1 の標準運用）。
  詳細な時刻が必要な場合のみ「初期設定」の `学習ログ時刻精度` を `分` に変更してください
- 受信時に既知のフィールドだけを残すため、想定外のデータは保存されません
- `source: "teacher"`（教師が入力した教材の操作記録）は受信時に破棄します

### タイピングの記録（Typa から自動作成）

タイピングに児童の手入力はありません。**Typa（`typa`）のレコードから自動で記録**されます。
まなびクエストの中でタイピングの数値を打ち込む画面はなくなりました。

- 対象は **通常出題（course）× 客観採点（objective）× ソロプレイ × 完走（completed）** のうち、
  **打鍵数を持つレコード**だけです。Typa の「ショートカット」ステージはキーを打った数を数えないため
  （`ext.keys` が 0）、学習ログ側にだけ残ります
- **20打に満たない回（`ext.eligibleForBest: false`）は転記しません**（仕様 §3.9）。
  数打で終えた回はたまたま速い数字が出やすく、最高記録にしてしまうと自己ベストもランキングも
  二度と更新できない値で埋まります。Typa がアプリの中で引いている線（`MIN_RECORD_KEYS`）を、
  まなびクエスト側でもそのまま使います。取り組んだ事実は「学習ログ」シートに残ります
- 「タイピング記録」シートの列は次のように埋まります

  | 列 | 入る値 |
  |---|---|
  | 日時 | 学習日（プライバシー保護のため日付まで。仕様 §4.1） |
  | 正しく打てた数 | `ext.correctKeys` |
  | 打った合計数 | `ext.keys`（打ちまちがいを含む） |
  | 正答率 | `100 × correctKeys / keys` |
  | ミス率 | `100 − 正答率` |
  | 速さ | `ext.kps` = **正しく打てた数 ÷ 秒** |

  > 打った合計数の項目名は仕様 §3.9 で `ext.keys` に確定しました。
  > 連携をつくった時期に使っていた旧名 `ext.totalKeys` も受け取れるようにしてあり、
  > どちらも無い場合は `correctKeys + missKeys` から組み立てます（`typingKeyCounts_`）。
  > ここで名前を取りちがえると、手入力を廃止した今は**タイピングの記録がまるごと消えます**。

> **Typa は「途中でやめる」のがふつうの使い方です**（仕様 §5.4）。
> 区切りを作らないことで、すきま時間の練習を成立させているアプリなので、
> `status: "aborted"` を**先生の画面の「中断」に数えません**。数えると、こまめに練習した児童ほど
> 「中断が多い子」に見えてしまいます。とりくみ量は `count` の合計と `activeMs` の合計で見てください。
> 対象アプリは `STUDY_ABORT_NORMAL_APPS` にまとめてあります。

- ランキング（タイピング速度）・バッジ（`TYPING_SPEED_MAX` / `TYPING_COUNT`）・速さのグラフ・
  学びの総量メーター（打った文字）・ポートフォリオPDF は、このシートを参照します
- **じこベスト（タイピングの速さ）とめあての達成判定も、受信のなかで行います。**
  記録の入口がここだけになったため、受信時に判定しないと「速さ◯打/秒」のめあてが
  永久に達成できなくなるからです（`receiveStudyRecords_`）
- 児童の「マイページ → きろくを見かえす → スピード」には、送信パネル・めあて・履歴・グラフが並びます
  （サーバー側でも `saveRecord` は `typing` を受け付けません）

> **「速さ」の数え方が変わりました。**
> 手入力だったころは「**打った合計数** ÷ 秒」でしたが、Typa からの実測になってからは
> 「**正しく打てた数** ÷ 秒」です。実測値になった以上、でたらめに連打したほうが
> 速さのランキングで上に行ってしまう数え方は使えないためです。
> 正しく打てているほど2つの数え方の差は小さいので、過去の記録との比較は続けられます。

### 100マス計算の記録（アプリのきろくから自動作成）

100マス計算に児童の手入力はありません。**100マス計算アプリのレコードから自動で記録**されます。

- 対象は **通常出題（course）× 客観採点（objective）× ソロプレイ × 完走（completed）** のレコードだけです。
  対戦・復習/にがて出題・自作問題・中断は、タイムや点数を同じ土俵で比べられないため学習ログ側にだけ残ります
- 「100マス計算記録」シートの列は次のように埋まります

  | 列 | 入る値 |
  |---|---|
  | 日時 | 学習日（プライバシー保護のため日付まで。仕様 §4.1） |
  | モード | `mode` を日本語化（`add`→たし算 など。未知の値は単元名） |
  | 問題数 | `summary.count` |
  | 点数 | **はじめの1回で解けた割合の100点満点換算**（`round(100 × firstTryCorrect / count)`） |
  | タイム | `elapsedMs` を秒に換算 |

- ランキング（100マスタイム）・バッジ（`CALC_COUNT` / `CALC_PERFECT_COUNT`）・タイムのグラフ・
  ポートフォリオPDF は、このシートを参照します
- `CALC_PERFECT_COUNT`（100点）は「ノーミスで解けた回数」を表します
- 児童の「マイページ → きろくを見かえす → スピード」には履歴とグラフだけが並びます
  （サーバー側でも `saveRecord` は `calc` を受け付けません）

### 読書の記録（どくしょ ちょきんばこ から自動作成）

読書にも児童の手入力はありません。**どくしょ ちょきんばこ（`reading-books`）のレコードから自動で記録**されます。
読書の記録はこのアプリでは行わず、読書アプリに一本化しています。

- 対象は **完走（completed）× ソロプレイ** のレコード（＝1冊）です。
  100マス計算とちがい `source` / `grading` では絞りません。手入力の本は `source: "custom"`、
  読書には採点がないため `grading` は常に `selfReport` ですが、どちらも「読んだ事実」としては同じだからです
- 「読書記録」シートの列は次のように埋まります

  | 列 | 入る値 |
  |---|---|
  | 日時 | 学習日（日付まで。仕様 §4.1） |
  | 題名 | `unit.title`（本のタイトル） |
  | ジャンル | **空**（手入力フォームがあった時代の列。読書アプリはジャンルを持ちません） |
  | ページ数 | `ext.pages` |
  | 評価 | `ext.rating`（児童がつけた★ 0〜5） |
  | 感想 | `ext.memo`（本を記録する画面で書いたかんそう。改行をつぶして200文字まで） |
  | ISBN | `ext.isbn`（13桁のときだけ。同じ本をまとめる鍵） |

- ランキング（どくしょ王＝ページ数）・バッジ（`READING_COUNT`）・ミッション（`RECORD_READING` /
  `TOTAL_READING_WEEK`）・学びの総量メーター・めあて（読書のページ数）・ポートフォリオPDF・
  みんなの本だな は、これまでどおりこのシートを参照します
- **みんなの本だな**は ISBN があれば ISBN で同じ本をまとめます（副題や表記ゆれで本が分かれません）
- 児童の「マイページ → きろくを見かえす → ことば」には冊数・ページ数と履歴だけが並びます
  （サーバー側でも `saveRecord` は `reading` を受け付けません）

> **読書は「時間」では見ません**（仕様 §3.8.2）。
> 読書アプリが計測しているのは「1冊を記録する操作」にかかった時間（数十秒）で、読書そのものの時間ではありません。
> そのため `elapsedMs` / `activeMs` は**合計学習時間・学習時間ランキング・時間ぶんの経験値から除外**し、
> 教員画面では冊数とページ数で表示します。経験値はかわりにページ数から計算します（下表）。

### 経験値・ごほうびへの変換

送るほど得になるよう、次の4種類を付与します（すべて「初期設定」で調整でき、0 で無効化できます）。

| ごほうび | 計算 | 設定キー |
|---|---|---|
| 学習時間ぶんの経験値 | レコードごとに `floor(活動時間の分数 × 係数)`（1件あたり上限まで）。**読書アプリは対象外** | `学習アプリ経験値係数` / `学習アプリ経験値上限` |
| タイピングぶん | タイピング記録1件ごとに `floor(速さ × (正答率/100) × 係数)`（手入力時代と同じ式・同じ設定項目） | `タイピング経験値係数` |
| 100マス計算の点数ぶん | 100マス記録1件ごとに `floor(点数 × 係数)` | `100マス計算アプリ経験値係数` |
| 読書のページ数ぶん | 読書記録1件（1冊）ごとに `floor(ページ数 × 係数)`（手入力時代と同じ式・同じ設定項目） | `読書記録経験値係数` |
| そうしんボーナス | **その日はじめての送信**に固定EXP | `学習ログ送信ボーナス経験値` |
| れんぞくボーナス | **その日はじめての送信**に `min(連続日数, 上限日数) × 係数` EXP | `学習ログ連続ボーナス係数` / `学習ログ連続ボーナス上限日数` |
| 交換ポイント | **その日はじめての送信**にガチャ・アイテム交換で使えるポイント | `学習ログ送信ボーナス交換ポイント` |

同一レコードIDの再送では二重付与されません。連続日数は「ログ」シートの `SEND_STUDY_LOG` から判定します。
獲得内訳は児童画面の結果ダイアログと「さいきんのできごと」に表示されます。

また、送信そのものがゲームの進行につながるよう次を用意しています。

- ミッション: `SEND_STUDY_LOG`（デイリー: きろくを送ろう）/ `RECORD_STUDY_APP`（ウィークリー: 5回学習しよう）/ `TOTAL_APP_WEEK`（協力: クラスで50回）
- バッジ: `APP_SEND_STREAK_DAYS`（7日れんぞく送信）/ `APP_RECORD_COUNT`（50回学習）/ `APP_MINUTES_TOTAL`（合計300分）
- ひろば: 「今週の学習アプリ時間」ランキング

## スクリプトを更新したとき

GAS のファイルを差し替えたあとは、メニュー **「① 初期セットアップ」を再実行**、続けて
**「③ 新しいミッション・バッジを追加」** を実行し、
**デプロイを更新（新しいバージョン）** してください。
（下部ナビゲーションバー・戻る操作・ポータル連携の修正は、デプロイを更新するまで反映されません）
不足しているシート・ヘッダー・設定項目だけが、既存データを壊さずに追加されます。

`appsscript.json` にはメール送信・トリガー設定の権限（`script.send_mail` / `script.scriptapp`）が
含まれているため、差し替え後に初めてアプリやメニューを実行する際は**権限の再承認**を求められることがあります。

## 技術メモ

- ランタイム: GAS V8 / タイムゾーン: Asia/Tokyo
- フロント: Bootstrap 5 + SweetAlert2 + Google Charts（SPA構成、`js_core` / `js_student` / `js_teacher` に分割）
- ふりがな: `kuroshiro` + `kuromoji`（CDN）で児童画面の漢字に `<ruby>` タグを自動付与。テキストノードだけを置換するためイベントやグラフを壊さず、入力欄・選択肢・グラフ描画先はルビ対象外。児童が入力した文章はHTMLエスケープしてから変換・注入するためXSSの心配なし。ライブラリが読み込めない環境（オフライン等）ではルビなしで通常動作。初回のみ辞書（数MB）を読み込み、以降はブラウザにキャッシュされます。なお kuromoji の内部で辞書URLの `https://` が `https:/` に潰れる既知バグがあり、GAS のサンドボックス上では辞書が 404 になるため、辞書取得の XHR だけ URL を補正するパッチを初期化中に当てています（60秒でタイムアウトし、失敗時はルビなしで続行）
- 学習ポータル連携: `doGet` は `XFrameOptionsMode.ALLOWALL`（`?embed=1` で余白を詰めた埋め込み表示）。
  GAS は `script.google.com` のページの中でさらに `googleusercontent.com` の iframe を作るため、
  ポータルに埋め込むと **ポータル ＞ ラッパー ＞ ユーザーコード** の3階層になります。
  そのため送信先は `window.parent`（ラッパー）ではなく **`window.top`**、
  ポータル側の送信先は `iframe.contentWindow` ではなく **受信した `event.source`** です。
  `postMessage` は双方向とも送信元を検証（アプリ側は「`window.top` かつ `*.github.io`」、
  ポータル側は「GAS のユーザーコンテンツ オリジン かつ `event.source.top === window`」）。
  やりとりするのは未送信件数・出席番号・送信結果・画面階層の状態と、
  本体経由で送るときの学習ログ（`RELAY_POST`）です。宛先は検証済みのオリジンに限定しています
- 画面階層（戻る操作）: `js_core` の `Nav` が復元手順をスタックで保持します。
  `showView(id, { push: true })` / `showRecordTab(id, { push: true })` / `navPush()` で積み、
  `goBackOne()` で1つ戻します。ダイアログ（SweetAlert2）が開いているときは、
  スタックを消費せずダイアログだけを閉じます
- 書き込み系 API はすべて `withLock_()`（LockService）で排他制御
- **書き込み系 API の戻り値**: 保存したあと、画面を書きかえるのに要るものは
  すべて戻り値に入れて返します（`newExp` / `newTotalExp` / `newExchangePoints` /
  `levelInfo` / `leveledUp` と、更新後の `missions` `goalData` など）。
  そうすることで、児童画面は保存のあとにデータを取り直さずに済み、
  「押した → 待たされる → また待たされる」の二段待ちがなくなります。
  経験値まわりは `addExp_()` と `readExpState_()` が `levelInfo` ごと返すので、
  新しい API を足すときもそのまま渡してください
- **すでに済んでいる操作**は、エラーではなく状態として返します
  （`claimMissionReward` の `alreadyClaimed: true` など）。
  通信が重なったときに、実際は成功しているのに警告が出るのを防ぎます
- 設定は `CacheService` で 5 分キャッシュ（変更後はメニューの「設定キャッシュをクリア」）
- **集計の性能**: ホームの初期表示では、ミッション進捗・バッジ判定・ランキング・最近のできごと・
  がんばりカレンダー・クラス共同目標が、いずれも「ログ」シートを必要とします。
  そこで `getAllLogRows_()`（`11_insights.gs`）が**1回の実行につき1回だけ**読んで全員で使い回し、
  `writeLog_()` が書き込みのたびにそのキャッシュを捨てます。
  記録シートも同様に `getRecordStore_()` が1回だけ読み、成長カード（今月・先月）と
  めあての進捗（週・月）はその結果をメモリ上で絞り込んで計算します。
  児童ごとの日別集計（`getInsights_`）は `CacheService` に5分だけ載せ、記録の保存時に明示的に捨てます
- **既存の集計との結合を避ける**: ミッション進捗（`countMissionProgress_`）は「ログ」の詳細文字列を
  正規表現でパースしていますが、今回追加した集計は**種別（3列目）だけ**を見ています。
  ログの文言を変えても、カレンダー・連続日数・ランキングは壊れません
- ことばアルバム・まなびレーダーは件数が多く重いため、「マイページ → きろくを見かえす → ことば」を開いたときだけ
  `getMyReflectionAlbum()` で取得します（ホームの初期表示には含めません）
- メールアドレス比較はすべて小文字化・trim 済みで統一
